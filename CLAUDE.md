# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

"MuscleNote", a personal gym workout tracker: a **native Android app** (Kotlin + Jetpack Compose) in `android-app/`, French by default with English. It is installed from the APKs of the GitHub Releases (users follow them with Obtainium); publishing on the Google Play Store is **not** planned, so store-compliance work is out of scope. The app is **offline**: no account, no workout data ever sent. It has two network accesses, both behind the `INTERNET` permission: the update check (SPEC § 3.17, D25, § 15.14, D39: one anonymous read of the latest GitHub Release, by a daily background job around 18:00 only while the « Nouvelle version disponible » notification is on, and on « Vérifier maintenant », nothing sent) and sending feedback to a Discord webhook, only when the user taps « Envoyer » (SPEC § 14, D26). Two opt-in on-device writes outside the app: the daily automatic backup to a user-picked folder (SPEC § 15.2, D28) and Health Connect (SPEC § 15.3, D29).

**`SPEC.md` is the single reference** for behaviour, data format, strings and decisions (§ 11; implementation status in § 13; features added after the switch-over, by batch, in § 15). Identity: `applicationId`/namespace `com.musclenote.android`, label « MuscleNote », minSdk 26, compile/targetSdk 37, portrait only.

**`DESIGN.md` is the reference for the interface**: colour tokens and their roles, Archivo type scale, spacing, radii, motion, icons, every component with its states, the 4 screen templates (hub, fiche, en direct, formulaire) and navigation — taken from the Claude Design export in `design/claude-design/`. Where it disagrees with the look described in SPEC (§ 2, § 9.1 – 9.3), DESIGN.md wins.

The app replaced an earlier Expo / React Native app (`com.musclenote.app`), removed from the repo but kept at the tag **`expo-final`** (`git show expo-final:artifacts/mobile/<path>`). SPEC paths such as `constants/i18n/fr.ts` refer to that tag. Users move their data over by sharing the Expo app's JSON backup to the native app (SPEC § 5.5); the backup keys keep the legacy `@gymtracker_` prefix for that reason.

## Interface rule

- Every interface uses the design-system tokens and components (`ui/designsystem/`, `Studio.colors` / `Studio.typography` / `Studio.spacing` / `Studio.shapes` / `Studio.motion`): **never a hard-coded colour or size** in a screen — no `Color(0x…)`, no literal `dp` / `sp`, no `TextStyle` built on the spot.
- Grouped lists (design « v2 listes groupées », SPEC D40): Journal, Paramètres and Nutrition are hubs with `grouped = true` (`HubTemplate` / `HubLazyTemplate`, margins 16, groups 32 apart) whose sections are `SectionHeader(grouped = true)` (caps label) + `ListGroup` (`HubSections.group` / `groupBlock` in the lazy hub); a `ListRow` inside a group takes its inset, inset divider and pressed colour from `LocalInListGroup`. Other screens keep the v1 sections (20 sp titles, rows on the background) until they are redrawn; the v2 colours apply everywhere.
- A new feature = one of the 4 templates + existing components. Create a new component only when none fits, put it in `ui/designsystem/components/` with `@Preview`s in dark and light, and add it to DESIGN.md (§ 9) in the same change.
- The redesign is complete (SPEC § 15.11): the legacy `ui/theme/`, Inter and the old Outlined icons are gone, and the whole app sits in one `StudioTheme` set by `MainActivity`. State-dependent weights (`FontWeight`) belong to components, never to screens; a success/error sentence is `StatusMessage` / `statusHelp`, a field under its label `LabeledField`.
- Large text (up to 200 %) must never clip: component heights are minimums (`heightIn`), texts wrap, numbers shrink instead of wrapping (`RollingText`, `FitText`), touch targets stay ≥ 48 dp, and value-only controls get a TalkBack description (e.g. `SetRow` `weightDescription`).

## Build, tests, releases

- Gradle Kotlin DSL + version catalog (`android-app/gradle/libs.versions.toml`), committed wrapper (checksum-pinned `distributionSha256Sum`). AGP 9 compiles Kotlin itself ("built-in Kotlin"): **never apply `org.jetbrains.kotlin.android` in a module** — the root build only declares it `apply false` to pin the Kotlin version (keep it equal to the Compose compiler plugin version).
- Local builds: the Android SDK command-line tools live in `~/Android/Sdk` (no Android Studio; platform `android-37.0`, build-tools 37.0.0, platform-tools, installed with `~/Android/Sdk/cmdline-tools/latest/bin/android --sdk=$HOME/Android/Sdk sdk install …`; AGP adds its own default build-tools on first build). Gradle finds it through the gitignored `android-app/local.properties` (`sdk.dir=/home/<user>/Android/Sdk`) or `ANDROID_HOME`. The system JDK (27) is fine for Gradle 9.8 / AGP 9. From `android-app/`: `./gradlew :app:testDebugUnitTest :release-notes:test` (JVM tests), `./gradlew :app:assembleDebug` (APK in `app/build/outputs/apk/debug/`). Signed release builds only happen in CI.
- Build type `preview` (`./gradlew :app:assemblePreview` → `app/build/outputs/apk/preview/app-preview.apk`): `initWith(debug)`, `applicationIdSuffix = ".preview"` (`com.musclenote.android.preview`), label « MuscleNote Preview » from `app/src/preview/res/values/strings.xml`, debug-signed. It installs beside the normal app with its own data (`adb install -r …`, wireless debugging); built locally only, never published. Anything tied to the package must keep using `${applicationId}` (FileProvider authority) so both apps can coexist.
- Compose previews (the before/after baseline for UI changes): `@Preview`s live in the **`debug` source set only**, `app/src/debug/java/com/musclenote/android/ui/preview/` — never in the release APK, and they don't touch app code. `PreviewTheme.kt`: multi-preview annotations, each rendering a light (« Clair ») and a dark (« Sombre ») variant in French — `@ComponentPreviews` (380 dp wide), `@ScreenPreviews` (411 × 1800 dp, whole scrolling screen), `@TallScreenPreviews` (411 × 2400 dp, Paramètres), `@PhonePreviews` (411 × 891 dp, what a phone shows). `PreviewData.kt`: realistic sample data (six weeks of Push / Pull / Legs, weigh-ins, supplements, today's tracking) around the fixed clock `PreviewTime` (Thursday 12 Nov 2026, 18:30), so renders never change from one day to the next. `PreviewContainer.kt`: `ScreenPreview(dataSet) { container -> … }` gives a real `AppContainer` loaded from temp files (`Full`, `WithCurrentWorkout`, `Empty`; no network, alarm or scheduled work) and a context whose `applicationContext` is a never-started `MuscleNoteApplication`. Previews: `ScreenPreviews.kt` (app with the navigation bar, every screen), one file per migrated area (`JournalPreviews.kt`, `LiveWorkoutPreviews.kt`, `ProgressPreviews.kt`, `NutritionPreviews.kt`, `SettingsPreviews.kt`: screens and their sheet contents), `SessionFormPreviews.kt` (start-session sheet, exercise picker, editor's rename and body-weight forms). A new screen or shared component gets its preview; a changed composable signature means updating its preview (they compile with every debug build). Design-system previews (DESIGN.md § 14) live in `app/src/debug/java/com/musclenote/android/ui/designsystem/`: one per component (`@StudioComponentPreviews`, 424 dp wide = a board column + margins), the two Claude Design component boards recomposed at their size (`BoardPreviews.kt`, 1400 × 1320) and the templates filled like the mockup screens (`TemplatePreviews.kt`, 412 × 915, mockup insets 40 / 24) — compare them with the export in `design/claude-design/` after any design-system change.
- Rendering previews to PNG: the Claude Code plugin `compose-preview@compose-agent-plugins` (marketplace `yschimke/compose-agent-plugins`) plus its CLI `compose-preview` in `~/.local/bin` (`compose-preview update` to upgrade, `compose-preview doctor` to check the setup). The CLI applies its Gradle plugin `ee.schimke.composeai.preview` itself (nothing in the build files) and renders with Robolectric; it downloads the Google Fonts the theme asks for (real Inter, cached in `~/.cache/composeai/fonts`). In Claude Code, use the MCP tool `render_preview` with `preview=<FunctionName>` (e.g. `SettingsScreenPreview`) and open the returned PNG. In a shell, from `android-app/`: `compose-preview show --json [--filter <name>]` → `app/build/compose-previews/renders/<Function>_<Clair|Sombre>-<hash>.png`. Never `./gradlew clean` or delete `build/` to chase a stale render (`render_preview` takes `force={reason}`).
- `.github/workflows/release.yml` runs on every push to `main` touching `android-app/**` (or the workflow itself): JVM tests, signed release APK (`versionName = 1.0.<run_number>`, `versionCode = 1000 + run_number` — above every former `v0.1.*` pre-release; keystore decoded from secrets into `$RUNNER_TEMP`, passed through `ANDROID_KEYSTORE_PATH` / `ANDROID_KEYSTORE_PASSWORD` / `ANDROID_KEY_ALIAS` / `ANDROID_KEY_PASSWORD`), signature check, then a normal (latest) GitHub Release `v1.0.<run_number>` with `MuscleNote-v1.0.<run_number>.apk`. The secret `DISCORD_WEBHOOK_URL` is passed to the release build step only and becomes `BuildConfig.FEEDBACK_WEBHOOK_URL` (`app/build.gradle.kts`: empty without it, a value that is not a Discord webhook URL fails the build). Follow with `gh run watch`, debug with `gh run view --log-failed`. The repo is public: never print signing details or the webhook URL in CI logs.
- Release notes (SPEC § 15.1, D27): the Release text lists the commit titles since the previous Release's tag (checkout with `fetch-depth: 0`), without merges nor commits touching only `*.md` / `.github/` / test source sets (`src/test*/`, `src/androidTest*/`); computed by the JVM module `android-app/release-notes/` (`./gradlew :release-notes:run`, tests `:release-notes:test`; the only module applying `org.jetbrains.kotlin.jvm`). **Commit titles describe the change for the user, in French** (« Sauvegarde automatique : choix du dossier », not « Refactor BackupViewModel »): they end up verbatim in the release notes.
- `.github/workflows/checks.yml` runs on pull requests to `main` touching `android-app/**`: JVM tests (app + release notes) and an unsigned release APK, no secrets. Use it to validate a branch before merging; only the merge publishes a Release.
- Tests: JVM unit tests in `app/src/test/` target the pure rules and the repositories (`unitTests.isReturnDefaultValues = true` because some code logs through `android.util.Log`); `StringResourcesTest` checks that FR and EN have the same keys and positional arguments.

## Architecture (`android-app/app/src/main/java/com/musclenote/android/`)

- Strings: `res/values/strings.xml` (FR, default) + `res/values-en/strings.xml`, keys converted from the Expo app's `constants/i18n/*.ts` (SPEC § 9.4). Language = system language, overridable FR / EN through `AppCompatDelegate.setApplicationLocales` (`MainActivity` is an `AppCompatActivity`).
- Navigation (SPEC § 15.8, D33): `ui/MuscleNoteApp.kt` — four tabs (`TopLevelDestination`: Accueil, Journal, Progrès, Nutrition) in the design-system `StudioNavigationBar`, Paramètres pushed above Home by the gear (tab bar kept, Accueil selected), the `MiniSessionBar` of the current workout on every hub except Home (whose highlight surface replaces it), fade transitions followed by the predictive back gesture (`enableOnBackInvokedCallback`). The workout is opened through `openWorkout()` (pops back to it if it is already in the stack, never twice) from the Home surface, the mini-bar and notification taps (`MainActivity.ACTION_OPEN_WORKOUT`). « Démarrer une séance » is a bottom sheet hosted once by `MuscleNoteApp` (`ui/workout/StartWorkoutSheet.kt`, type then body weight on the keypad, `BodyWeightForm.kt`); the exercise picker is a bottom sheet (`ui/workout/ExercisePickerSheet.kt`) opened by the live workout and by the completed-workout editor (`ui/workout/EditWorkoutScreen.kt`, `FicheLazyTemplate` with a bottom action: « Enregistrer » or the keypad); no `start-workout` / `exercise-picker` routes. Home (`ui/home/`), Journal (`ui/journal/`, lazy hub, one section per ISO week), Progrès (`ui/progress/`, lazy hub: body-weight surface, exercises by muscle group, calories and water, weigh-ins; « Nouvelle pesée » on the keypad) the exercise fiche (`ui/exercise/ExerciseFicheScreen.kt`, route `exercise-history/{exerciseId}`, `FicheLazyTemplate`), the workout summary (`ui/summary/WorkoutSummaryScreen.kt`, route `workout-summary/{workoutId}?finished=`, `FicheLazyTemplate`; SPEC § 15.12, D37: replaces the workout after « Terminer la séance », « Terminer » alone back to Home; also what a Journal / « Dernière séance » row tap opens, ← and ⋮ = the long-press actions; pure rules — same-program comparison, records broken — in `data/workout/WorkoutSummaryRules.kt`), Nutrition (`ui/nutrition/`, hub: « Aujourd'hui » surface `DailySurface`, supplements with a separate « taken today » check; calories / water / goals on the keypad, new supplement, supplement reminders and time picker in `NutritionSheets.kt`; SPEC § 15.10) and Paramètres (`ui/settings/SettingsScreen.kt`, second-level hub: grouped `ListRow`s, each setting opened in a bottom sheet) are migrated to `Studio`; their pure rules live in `data/home/HomeRules.kt` (highlight, suggested session type) and `data/journal/JournalRules.kt` (week grouping, summaries, totals). Session rows and their long-press actions (edit, date, delete) are shared in `ui/journal/SessionRows.kt`; live clocks (elapsed, rest) in `ui/workout/LiveClock.kt`.
- Theme: the design system only (`ui/designsystem/theme/`: `StudioColors` dark and light palettes, Archivo embedded in `res/font/archivo.ttf`, no downloadable fonts); choice Dark (default, SPEC D35) / Light / System in preferences, a stored choice is never rewritten; muscle groups have no colour (shown as text). The chosen theme is also handed to the system (`ui/designsystem/theme/SystemNightMode.kt`, Android 12+) so the splash follows it. Icons: Material Symbols Rounded vectors `res/drawable/ds_ic_*.xml`; the only other drawables are the notification action icons (`ic_check`, `ic_replay_30`, `ic_forward_30`, `ic_skip_next`), `ic_notification` and the logo layers. Charts: the design-system Canvas `TrendCurve` / `CompactTrendCurve` / `MiniTrendCurve` (`ui/designsystem/components/TrendCurve.kt`, pure geometry in `CurveGeometry.kt`; SPEC § 15.9, the old `LineChart` is gone); date/number display helpers (`DateFormats`, `formatNumber`, `formatInteger`) in `ui/components/DisplayNames.kt` — always format with `appLocale()` (the locale of the displayed texts, `data/util/AppLocales.kt`, French when the system language is neither FR nor EN), never `locales[0]`.
- Data: one repository per domain in `data/repository/` (`StateFlow` + `Mutex`, one `JsonDocument` file per document in `filesDir/data/`, atomic writes, unreadable files set aside as `*.corrupt-<ms>.json`); pure business rules live beside them (`data/workout/WorkoutRules.kt`; statistics — streak, gym time, volume, 1RM, per-exercise history — in `WorkoutStats.kt`, Progrès tab calculations (§ 3.10) and the per-exercise metric (load, reps at bodyweight, duration) in `data/progress/ProgressStats.kt`, curve rules (periods, last-session summary and variation, downsampling) in `data/progress/ProgressCurves.kt`, weigh-in rules in `data/nutrition/BodyWeightRules.kt`, all counting completed sets only) and are what the JVM tests target. Device-only settings (not in backups) go to `local_preferences.json` via `PreferencesRepository.localPreferences` (migrate-card dismissal, and a copy of the in-app language that `withAppLocale()` reads before Android 13, when AppCompat only knows it once an activity exists). Screens never keep their own copy of persisted data and call repository mutations through `AppContainer.launchMutation { … }` (undispatched start on the fair `Mutex`, so keystrokes apply in order and survive leaving the screen). The in-progress session is written with a 300 ms debounce and flushed on `ON_STOP`.
- Notifications (`notifications/`, shared by the workout notification, the rest timer and the supplement reminders): `AppChannel` (the three SPEC § 7.1 channels, names re-applied in the app language at app start and every activity creation; the old `rest-timer-ongoing` channel is deleted), `ExactAlarms` (exact `RTC_WAKEUP`, inexact fallback), `AppNotifications.post` (silently skipped when notifications are denied), texts built through `Context.withAppLocale()`. Rest timer: `RestTimerRepository` (one rest, `rest_timer.json`, `adjust(±30)`; Android effects behind `RestTimerEffects` = end alarm + « Repos terminé » alert, a no-op in JVM tests) + `RestTimerNotifier` + `RestTimerReceiver`; the end alarm is the only source of the « rest finished » event, and `AppContainer.endWorkout()` / 24 h finalisation stop the rest.
- Workout notification (SPEC § 15.5, D31): one ongoing « Séance en cours » notification replaces the old rest notification — pure content and « next set » rule in `data/workout/WorkoutNotificationRules.kt` (texts come from the resources, tests read the real `strings.xml`), Android side `notifications/WorkoutNotifier.kt` behind `WorkoutNotifications` (Live Update request on Android 16+, `POST_PROMOTED_NOTIFICATIONS`). `AppContainer` republishes it on every change of the current workout / rest / custom exercises (throttled, latest state always posted, one post at a time) and right after each action; actions (« Valider la série », ±30 s, « Passer ») go through `RestTimerReceiver` → `AppContainer.completeNextSet()` / `adjustRest()` / `skipRest()`. Ongoing notifications are not bridged to watches: the watch gets the « Repos terminé » alert, which carries « Valider la série ». No foreground service (system chronometer).
- Supplement reminders (SPEC § 7.3): pure rules in `data/nutrition/` (`NutritionRules`, `ReminderSchedule` — next local wall-clock occurrence, DST-safe), Android side `SupplementReminderScheduler` behind the `SupplementReminders` interface (serial queue re-reading the latest supplements; alarm identity = `musclenote://reminder/{supplementId}/{reminderId}`), `SupplementReminderReceiver` (re-reads, notifies, reschedules tomorrow) and `ReminderResyncReceiver` (boot, package replaced, time/time-zone change, exact-alarm permission). `NutritionRepository` syncs alarms after every supplement change; `AppContainer` does a full resync at start-up and after an import. The current local day is `AppContainer.currentDay` (midnight timer, foreground, time-zone change); UI reads it through `rememberToday()`.
- Backup & export (Paramètres, `ui/settings/BackupViewModel.kt`): JSON v2 backup through `data/backup/` (`BackupWriter`; `BackupReader` = parse → version check → per-key validation → migrations → normalisation, v1 from the Expo app still imported) and `AppContainer.importBackup`, which also receives files shared by other apps (`SEND`/`VIEW` intent filters on `MainActivity`); CSV export is the pure `data/export/CsvExport.kt` (headers/format supplied by `CsvExportTexts`). Files are shared from `cacheDir/exports/` through the `FileProvider` (`res/xml/file_paths.xml`).
- Automatic backup (SPEC § 15.2, D28): `AutoBackupRepository` (`auto_backup.json`, device-only, loaded once at start, never replaced by an import) writes the same JSON v2 as the manual export (`AppContainer.exportBackupJson`) to `musclenote_backup_<local day>.json` in a folder picked with `OpenDocumentTree` (persistable URI grant), replacing the same day's file, then keeps the 14 most recent (pure rules in `data/backup/AutoBackupRules.kt`); folder access behind `BackupFolders` (`backup/SafBackupFolders.kt`, `DocumentsContract`; access errors → `BackupFolderUnavailableException` → « dossier inaccessible »), schedule behind `AutoBackupScheduler` (`backup/AutoBackupWorker.kt`: unique periodic WorkManager work `auto-backup`, 24 h, first run 24 h after enabling since enabling backs up directly). WorkManager's `FOREGROUND_SERVICE` is removed from the merged manifest (no foreground work): don't add work needing it without restoring it; `ACCESS_NETWORK_STATE` is kept for the update check's network constraint. UI: row + sheet in `ui/settings/AutoBackupSettings.kt`.
- Health Connect (SPEC § 15.3, D29, D30): write-only (`health.WRITE_EXERCISE`, `health.WRITE_WEIGHT`, no read). Pure conversion in `data/health/HealthRecords.kt`: every finished workout → strength-training session (start/end + zone offsets; under 10 min or no duration → the § 3.7 gym-time estimate `WorkoutStats.countedMinutes`, else 10 min, never ending after it was ended in the app); **one weight per local day** with the Progrès rule (`BodyWeightRules.dailyWeights`, shared with `ProgressStats.bodyWeightSeries`: the weigh-in, else the latest workout's body weight); stable `clientRecordId`s `musclenote-session-<id>` / `musclenote-weight-<yyyy-MM-dd>`, type read from the prefix (the v1.0.5 ids `musclenote-weight-workout-<id>` / `musclenote-weight-weighin-<date>` still read as weights, deleted and replaced through `legacyWeightReplacements`); fingerprints of what is written, title excluded, SDK mapping in `health/HealthConnectRecords.kt` (manual-entry metadata, `clientRecordVersion` = `max(last + 1, now ms)` so an upsert replaces), device access behind `HealthConnectGateway` (`health/AndroidHealthConnectGateway.kt`, titles in the app language at send time). `HealthSyncRepository` (`health_connect.json`, device-only: enabled, sent ids → fingerprints, pending ids) — `AppContainer.watchHealthChanges()` diffs the fingerprints of finished workouts + weigh-ins on every change (imports included; the loaded state is the baseline, so older data only goes through « Envoyer l'historique ») and enqueues the changed ids; `sync()` re-enqueues sent records whose source changed or vanished, then, type by type (one type per Health Connect call, a failing type doesn't block the other), deletes (only ids in the registry) and upserts in batches of 100; only what Health Connect confirms (`insertRecords` ids, `upsert` returns the count) enters the registry and leaves the queue, and « Envoyer l'historique » reports those confirmed counts plus per-type failures; failures keep the queue (retried on the next change, on foreground, on « Envoyer l'historique »). The section is hidden unless `getSdkStatus == SDK_AVAILABLE`. The privacy-policy screen `health/HealthPermissionsActivity.kt` is mandatory (`ACTION_SHOW_PERMISSIONS_RATIONALE` + the `VIEW_PERMISSION_USAGE` / `HEALTH_PERMISSIONS` activity-alias): without it Health Connect silently refuses the permission request. Works for apps installed outside the Play Store. UI: row + sheet in `ui/settings/HealthConnectSettings.kt`.
- Update check and notification (SPEC § 3.17, § 15.14, D25, D39): `UpdateRepository` (`update_check.json`, not in backups: last check, ignored version, the « Nouvelle version disponible » choice — `null` = default, off when Obtainium installed the app (`update/InstallSource.kt`: Obtainium, or the Play Store name it borrows through Shizuku), on otherwise — and the last notified version) reads the latest release through `ReleaseSource` (`update/GitHubReleaseSource.kt`: one anonymous `GET` to the GitHub API, `HttpURLConnection`, no extra dependency); pure rules (tag `v1.0.n` → versionCode `1000 + n` compared to the installed `versionCode`, other tags by version numbers, notify-or-not, next 18:00, first line of the notes, JSON parsing) in `data/update/UpdateRules.kt`. The only automatic check is the daily WorkManager job `update-check` (`update/UpdateCheckWorker.kt`: one-time work around 18:00 local, `CONNECTED` constraint — hence `ACCESS_NETWORK_STATE` is kept — re-enqueued by itself with `APPEND_OR_REPLACE`, never `REPLACE` from inside the job), scheduled only while the setting is on; nothing on foreground. It posts `notifications/UpdateNotifier.kt` (channel `updates`, single id so a newer version replaces the shown one, « Voir » = Obtainium's launch intent or the release page, « Ignorer cette version » through `UpdateNotificationReceiver`); « Vérifier maintenant » never notifies. `BuildConfig.UPDATE_NOTIFICATIONS` is false in the `preview` build type (no job, no notification, row hidden). UI: the « Mise à jour disponible » section of Home (`ui/home/HomeScreen.kt`, not when installed by Obtainium, « Plus tard » = ignore the version), the « Nouvelle version disponible » check row of Paramètres › Notifications and the version / « Vérifier maintenant » / « Télécharger la … » or « Ouvrir Obtainium » rows of « À propos » (`ui/settings/UpdateRows.kt`). « Download » opens the APK in the browser; the app never downloads or installs anything itself.
- Feedback (SPEC § 14, D26): pure rules in `data/feedback/FeedbackRules.kt` (Discord payload built with kotlinx.serialization — one embed, `allowed_mentions: {parse: []}` —, trimming/truncation counted in code points, one send per minute, 429 delay from `retry_after` / `Retry-After`); `FeedbackRepository` (draft in memory only, delays in `feedback.json`, not in backups, one send at a time); `feedback/DiscordWebhookSender.kt` (`HttpURLConnection` POST behind `FeedbackSender`); `ui/settings/FeedbackSheet.kt` (fields keep local text, copied to the draft on each keystroke and re-initialised when `resets` changes after a successful send). Without a webhook URL at build time, `AppContainer` gets no sender and the « Envoyer un avis » row is hidden. The URL ships in the public APK, so it is not secret from anyone who unpacks it.
- Crash reports (SPEC § 10.9): `CrashHandler` is installed first in `MuscleNoteApplication.onCreate`, writes `filesDir/crashes/crash-<ms>.txt` through the pure `data/crash/CrashReports.kt` (5 most recent kept), flushes the in-progress session, then delegates to the default handler; Paramètres shows the « Rapport de plantage » row (`ui/settings/CrashReportSettings.kt`, sheet: share the latest / delete all) only when a report exists. Nothing is sent over the network.

## Leftovers

The gitignored `.local/` directory is leftover state from the Replit environment the project started in, not app code.
